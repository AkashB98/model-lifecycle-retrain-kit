# model-lifecycle-retrain-kit

**The train → deploy → monitor → gated-retrain loop for a small credit model, implemented end to end from scratch.**

Most portfolio ML repos stop at "train a model, report a score." Production models don't stop there: the world drifts, performance decays, and someone has to decide — with a rule declared *before* the fact, not vibes after it — whether to retrain, and whether the new model has actually earned the champion seat. This repo builds that whole lifecycle for a synthetic credit model: a from-scratch logistic regression, a JSON model registry, exactly two monitoring triggers, and a champion/challenger promotion gate. Both outcomes are demonstrated: in the drifted period the gate promotes the challenger; in the no-drift control nothing retrains at all.

> **Synthetic data only.** Every borrower is fictional, generated by a seeded generator (seed 42). No real borrower, account, or portfolio data anywhere.

Stdlib-only Python 3. Zero third-party imports, zero network, zero API keys.

## What this does NOT demonstrate

Plainly: **this repo does not demonstrate XGBoost or MLflow.** There is no gradient boosting and no experiment-tracking server here. What it demonstrates is the *lifecycle logic* — training, a versioned registry, drift/AUC triggers, and champion/challenger gating — with from-scratch standard-library implementations of every piece (logistic regression by gradient descent, rank-based AUC, PSI). The point is that the loop's decisions are inspectable line by line, not hidden inside a framework.

For periodic governance *evidence packs* (auditor-style validation artifacts), see the sibling repo `model-governance-evidence-kit` — this repo deliberately does not rebuild that; its monitoring stays narrow by design.

## Quickstart

```bash
python3 cli.py generate                       # dataset summary (seed 42)
python3 cli.py train                            # train champion v1 on period 1
python3 cli.py monitor --scenario drift       # the two monitoring checks (JSON)
python3 cli.py retrain --scenario drift       # full loop; writes registry.json
python3 cli.py check --scenario drift; echo $?  # 1 = trigger fired
python3 cli.py check --scenario control; echo $? # 0 = healthy, no trigger
python3 demo.py                                 # both scenarios, end to end
python3 -m unittest discover -s tests           # 33 tests
python3 evals/run_evals.py                      # 8 golden evals
```

`check` exit codes: **0** = no trigger, **1** = a monitoring trigger fired, **2** = data/IO error (e.g. a named registry file does not exist).

## POC framing

- **Problem:** a credit model approved on period-1 data silently decays when the population and the outcome relationship move. Retraining on every wobble wastes effort and can promote worse models; never retraining ships a stale champion.
- **Success criteria, declared up front:** (1) monitoring fires on the planted-drift period and stays silent on a no-drift control; (2) a challenger is trained *only* when a trigger fires; (3) promotion requires beating the champion on a fresh holdout by a pre-declared margin (AUC ≥ champion + 0.01) *and* not worsening calibration (Brier); (4) every headline number is pinned by a golden eval and reproduces byte-for-byte.
- **Result:** all four criteria met on the seeded data — see the headline table below; the drift challenger is promoted, the control never retrains, and a challenger that fails the margin (or Brier) is rejected by the gate.

## The lifecycle

1. **Train.** Logistic regression from scratch: features standardized on the training split, full-batch gradient descent (400 epochs, lr 0.1, L2 0.01). Features: `income_k`, `utilization`, `delinquency_count`, `tenure_years`; binary default outcome.
2. **Registry.** `registry.json` holds every version: version id, period trained on, feature list, coefficient hash + summary, holdout AUC, Brier score, and calibration by decile (mean predicted vs observed), plus status — `champion` / `challenger` / `archived`. Promotion archives the old champion; nothing is silently overwritten.
3. **Monitor (narrow, exactly two checks).**
   - **PSI on `utilization`** — population stability index over 10 equal-width bins, shares floored at 0.0001; trigger threshold **PSI > 0.25**.
   - **AUC drop** — champion AUC on the production period vs its period-1 holdout reference; trigger threshold **drop > 0.03**.
4. **Gated retrain.** Only if a trigger fires, a challenger is trained on the recent period alone and scored against the champion on a *fresh* holdout neither was trained on. Promote only if AUC ≥ champion + 0.01 **and** Brier ≤ champion's. Otherwise the challenger stays a challenger and the champion keeps its seat.

## Headline numbers (seed 42, pinned by golden evals)

| Quantity | Value |
|---|---|
| Champion v1 AUC, period-1 holdout (n=400) | **0.783209** (Brier 0.135441) |
| PSI on utilization, drift period | **1.11443** → trigger (threshold 0.25) |
| Champion AUC on period-2 fresh holdout | **0.725005** (drop **0.058204** → trigger, threshold 0.03) |
| Challenger v2 AUC on the same fresh holdout | **0.786853** (Brier 0.132616, beats champion's 0.157881) |
| Gate decision, drift scenario | **PROMOTE** — v2 champion, v1 archived |
| PSI on utilization, no-drift control | **0.044039** → no trigger |
| Control scenario | no trigger → **no retrain**, champion stays v1 |

The planted drift is twofold: the utilization distribution shifts up (mean 0.42 → 0.62), and the true outcome relationship rotates — income matters much more in period 2, while utilization, delinquency history, and tenure matter much less. The period-1 champion leans on exactly the features that stopped mattering, which is why it decays and why a retrained challenger genuinely wins rather than winning by construction noise.

A third case is pinned at the gate level (eval G6, unit tests): a challenger trained but **rejected** — one that beats the champion by less than the 0.01 margin, and one that wins on AUC but is worse on Brier. Both stay unpromoted.

## Architecture

| Module | Job |
|---|---|
| `generator.py` | Seeded synthetic borrowers; period 1, drifted period 2, and a no-drift control period, each with train/recent + holdout splits |
| `model.py` | Logistic regression from scratch: standardization, full-batch gradient descent, L2, stable sigmoid, coefficient hashing, (de)serialization |
| `metrics.py` | AUC from scratch (Mann–Whitney rank formula, tie-averaged) + brute-force pairwise cross-check, Brier score, PSI from scratch, calibration by decile |
| `registry.py` | JSON registry: version entries with metrics + calibration, champion lookup, promotion (archives the predecessor) |
| `lifecycle.py` | The two monitoring checks with stated thresholds, the pure promotion gate, and the full per-scenario loop |
| `cli.py` | `generate` / `train` / `monitor` / `retrain` / `check` (exit 0/1/2) / `demo` |
| `demo.py` | Both scenarios end to end with asserts: drift promotes, control stays put |

## Development loop — what building this actually caught

The first drift design failed its own demo, honestly and instructively. The period-2 relationship was made "stronger in the same direction" (bigger same-sign coefficients), and two things went wrong: the default rate collapsed from ~21% to ~5% (the intercept no longer balanced the larger income term), and — worse — the champion's AUC on period 2 *rose* to 0.815 from 0.783. A model with the wrong relative weights still ranks well when every true effect keeps its sign and the total signal grows; "the relationship changed" is not the same as "the old model got worse." The fix was to *rotate* the relationship instead of amplifying it (income's effect up, the other three down, intercept rebalanced to hold the base rate near period 1's), which dropped the champion to 0.725 while leaving a challenger something real to recover. The pinned evals now guard exactly that property: if a future edit makes the drift cosmetic again, G3 and G4 fail.

## Scope and honest limits

- **Synthetic data, planted drift.** The drift is built in at known sizes, so "the triggers find it" proves the machinery, not that real decay looks like this.
- **Logistic regression only.** One linear model, four features. No trees, no boosting, no neural nets — the lifecycle is the subject, not model class.
- **PSI is one check, not a monitoring suite.** One feature, one statistic, plus the AUC-drop trigger. No segment slicing, fairness checks, latency/data-quality monitoring, or alerting — production monitoring needs all of those; the sibling governance kit covers the periodic-evidence side.
- **Thresholds are declared, not learned.** PSI 0.25, AUC drop 0.03, margin 0.01 are stated conventions for this POC; a real deployment would calibrate them against historical volatility and the cost of a bad promotion.
- **The fresh holdout is from the same planted period.** A real gate would also want a time-separated validation window and a shadow/canary phase before full promotion; the registry's status field is where those stages would live.

## Why this project

Forward-deployed and analytics work rarely ends at the first model — it ends at the tenth retrain decision nobody wants to make on gut feel. This repo makes those decisions mechanical and auditable: triggers with stated thresholds, a gate with a pre-declared margin, a registry that remembers every version's evidence, and a control case proving the loop knows when to do nothing.
